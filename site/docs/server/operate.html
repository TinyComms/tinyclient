Operate and upgrade

Upgrades, backups, suspension, logs, and every optional setting.

Commands run from deploy/, next to compose.yml and .env.

Upgrade

Back up the database first, then pull and rebuild:

docker compose exec -T postgres pg_dump -U postgres tinyserver > backups/before-upgrade.sql
git pull
docker compose up -d --build --remove-orphans

tinyserver-init applies any new migrations and exits before the server starts. If it fails, the server does not start; docker compose logs tinyserver-init says why.

Going back to an older release means restoring that backup: an older binary refuses a database that has migrations it does not know.

Some releases need a step from you, such as the one that moved the sign-in choice into the app. Upgrading in deploy/README.md lists them. Read it before each upgrade.

Running a published image

Every push to main that passes CI is published as ghcr.io/tinycomms/tinyserver:<sha> and :main. compose.image.yml runs that image instead of building one on the host. Name the sha, not :main, so the host runs the commit you chose and going back is naming the one before.

docker compose exec -T postgres pg_dump -U postgres tinyserver > backups/before-upgrade.sql
TINYSERVER_IMAGE=ghcr.io/tinycomms/tinyserver:<sha> \
  docker compose -f compose.yml -f compose.image.yml up -d --pull always --remove-orphans

TINYSERVER_IMAGE can live in the environment file instead. The binary carries its migrations; the checkout is still where the compose files and the Postgres init script come from.

Stop

docker stop sends SIGTERM. The server ends every call, finishes the requests it has, and exits. Calls live in memory, so a restart ends them.

Back up, restore and move

tenant/operator.sh works on a single community when given --stack .env. Backups are encrypted with age, which has to be on the host.

sh tenant/operator.sh backup  --stack .env --out community-2026-11-01.age --recipient age1...
sh tenant/operator.sh restore --stack .env --in community-2026-11-01.age --identity operator.key
sh tenant/operator.sh export  --stack .env --out community-export.age --recipients-file owner.txt

A backup holds the database, the uploads, Pocket ID’s data, the secrets, and the server’s end-to-end key file. That key is not in the database, so a plain pg_dump does not contain it. Losing the key file and its database row together stops the server from starting, rather than making a key that members’ apps would reject.

export writes the same to hand to someone who will run the community elsewhere. delete removes it and asks for the name again with --confirm.

Suspend and hold

CommandEffect
statusThe mode, the notice, since when, and whether there is a hold
suspend --read-only --notice TEXTReading, signing in and out, deleting your account and filing a report still work. Every other write is refused. Calls already running go on until they end; new ones are refused.
suspend --offline --notice TEXTOnly the health and status routes answer. Open connections close within a minute.
resumeNormal again. The notice is cleared.
hold --reason TEXT, releaseA legal hold. Resolved reports stop expiring, and operator.sh refuses to delete or overwrite the community.

Members see the notice, 1 to 500 characters. The public status route never says whether there is a hold.

Logs

The server logs on its own machine only. There is no exporter and no telemetry.

  • The log is stderr; Docker keeps three files of 10 MB. The level is info unless TINYSERVER_LOG_LEVEL says error, warn, debug or trace. RUST_LOG is ignored.
  • A debug ring of about 2,000 lines, none older than an hour, stays in memory. It is written to disk only when the process receives SIGUSR1, and bundles older than 24 hours are deleted on the next start.
  • Message text, filenames, tokens, keys, invite secrets, email addresses, display names, and call setup (SDP) are never recorded. Ids such as user_id, room_id and call_id are.
  • Client addresses are kept out of the log unless TINYSERVER_LOG_PEER_IP=on, and then only on the debug ring.

During a call the log has a media counters line once a minute. Calls and media says how to read it.

Housekeeping

Every ten minutes the server deletes expired sessions, expired invites nobody used, sign-ins nobody finished, one-time codes nobody redeemed, uploads never attached to a message after an hour, and resolved reports past their retention. Accepted invites stay in the invite list.

Scanning off

docker compose -f compose.yml -f scan-off.yml up -d

This runs without clamd and marks every upload clean without scanning it. It is only for a community whose attachments are sealed on the sending device, where the server could scan nothing but ciphertext. Anywhere else it lets any file through.

Many communities on one host

tenant/tenant.sh runs the same compose file once per community, each with its own project, networks, volumes, subnet, media port, database, roles, passwords and secrets.

sh tenant/tenant.sh new acme --chat-url https://acme.example.org \
    --auth-url https://auth.acme.example.org --tunnel-token <token>
sh tenant/tenant.sh compose acme up -d

deploy/tenant/README.md has the rest.
