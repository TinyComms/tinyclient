Server privacy and security

What a Tiny server stores, what the person who runs it can read, and what it does not protect against.

A Tiny server is run by its owner, not by the tinyclient project. Joining one means trusting whoever runs it with what is listed here. This page is about the server; Privacy and security is about the app on your computer.

What the server stores

DataHow it is kept
PasswordsNone. There are none.
AccountsA display name and an optional picture. An email address only if a sign-in provider sent one and the owner chose to keep it. There are no usernames.
PasskeysThe public key, a counter, a label, and when it was made and last used. Recovery codes as hashes.
Sessions, invites, bot tokensOnly a hash of each token. A session has no address, user agent or device name beside it.
Plaintext messagesThe text, in the database
Encrypted messagesCiphertext, with who posted it and when
FilesOne file each on the upload volume, under a random name. A plaintext upload is plaintext on disk; a sealed one is stored as it arrived.
CallsNothing. No recording. A call between two people leaves one line in their conversation saying how it ended.
Audit logWho did what to whom, with any reason they typed
Device namesAn optional label for each device used with encrypted conversations
IP addressesNo table holds one. The call server holds participants’ addresses in memory during a call.

The stack does not encrypt the database or the volumes on disk. That is the host’s to do.

What the operator can read

The person with the database owner role or root on the host can read every plaintext conversation and attachment, any email addresses, the audit log and every abuse report. They can sign in as any member, make themself an owner, and restore an older backup. Reading leaves no trace.

They cannot read the text of an encrypted conversation, the contents, names or types of sealed files, or the audio of an end-to-end encrypted call.

Roles do not change this. A moderator sees what their permissions show in the app; the operator is whoever holds the machine.

What the server always sees

  • Who is a member, who talks to whom, and when. The record that two people have a direct conversation outlives either account.
  • For encrypted conversations: who posted, in which conversation, the minute, the size, and the number and sizes of attachments.
  • For calls: who is in which call, when they joined and left, who is speaking, packet sizes, and each participant’s address.
  • When each member was last online, unless the owner chose not to record it.

Other members learn who is on the server and, in a call, the host’s public address. They do not learn each other’s addresses from the server.

A Tiny server is not an anonymity system.

Logs and telemetry

  • The server sends no analytics, no crash reports and no update checks. Its log stays on its own machine.
  • There is no HTTP access log.
  • Never logged: IP addresses, message text, filenames, tokens, email addresses, display names.
  • Logged by default: sign-ins and connections opening and closing, with the account’s id, and moderation with ids. That is a history of who was connected and when, so this is not a server that keeps no logs.
  • Redaction works by field name, and a crash message bypasses it.

Operate and upgrade has the settings.

What is on the network

  • The server does not do TLS itself; the tunnel or proxy in front of it does. With the default Cloudflare tunnel, Cloudflare ends TLS and can see every request, session tokens and plaintext content included. A proxy of your own avoids that.
  • One port is published: the media port. The web port is not.
  • The server makes no outbound connections, except to a sign-in provider outside its own compose file when one is configured. The scanner fetches virus signatures, so its mirrors see the host’s address.
  • /health answers without a session.

Retention and deletion

Nothing deletes messages, audit rows or bans by age. There is no auto-delete setting.

WhatKept for
A session30 days unless the operator set otherwise. Not extended by use.
The replay of live events24 hours
An upload never attached to a message1 hour
An invite nobody usedUntil it expires: 7 days unless set
A resolved abuse report90 days unless set, or for as long as an owner holds it
  • Deleting a message, which only its author can do, removes the text, the attachments and the reactions. A marker with the author and the times stays.
  • A kick removes the membership and every session. A ban does the same and is kept until lifted. The person’s messages stay in both cases.
  • Sign out everywhere ends every session; open connections close within a minute.
  • Deleting an account removes the email address, name, picture, sign-in identities, passkeys, recovery codes, sessions, and the text and attachments of every message the person wrote. It keeps the markers where those messages were, the record of who they had direct conversations with, audit rows, and bans. A sole owner cannot delete their account. It does not delete an account at Pocket ID or another provider.

No deletion reaches the database’s write-ahead log, earlier backups, other people’s copies, or a proxy’s logs. Deleted files are unlinked, not overwritten. Restoring a backup brings back what was deleted after it. Backups have no schedule or expiry of their own.

What it does not protect against

  • There has been no independent security review, penetration test or cryptographic audit.
  • The passkey sign-in pages are tested against a software authenticator, not a real browser.
  • There is no per-member storage quota: a member can fill the disk with uploads.
  • The media port has no protection against a flood of traffic.
  • A member cannot list their own sessions, only end them all.
  • A plaintext upload is written to disk before the scan verdict comes back. Nobody can fetch it until it passes.
  • A legal hold stops resolved reports from expiring. It does not stop a member deleting their messages or their account.
  • The limits of the encryption apply.

The full account

The repository’s docs/privacy/ has the guarantees with the test behind each, the threat model, the data flows, and the open findings. Where those documents and this page differ, the repository is right. Some of them were written before the server had passkeys of its own and still describe sign-in through a provider only.
